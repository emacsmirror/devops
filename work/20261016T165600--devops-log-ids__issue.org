#+TITLE: Block IDs
#+PROPERTY: header-args:sh :results output
#+TARGET: .. (local)

* Issue

The =result= line of an async run can carry the wrong run ID: the first
UUID that appears in the block's *output*, not the ID of the run.

** What was seen

From devops.bb's sandbox work. The =execute= line has the right ID; the
=result= line for the same run has another:

| time     | event   | line | id in the log | run that ID names               |
|----------+---------+------+---------------+---------------------------------|
| 10:49:16 | execute |  262 | =3b71952d…=   | the =tail -n 2 \| jq= block (ok)|
| 10:49:19 | result  |  262 | =6628f1b2…=   | an earlier =jq select(…)= block |
| 10:50:36 | execute |  275 | =d75b29c1…=   | the =tail -n 4 \| jq= block (ok)|
| 10:50:36 | result  |  275 | =6628f1b2…=   | the same earlier block          |

Checked with =devops-bb run-output= on each ID: =6628f1b2…= has the
input of a block that ran minutes before. In the whole log, that ID is
on four =result= lines and no other result ID repeats.

** Why

Both blocks printed the log, and the log holds =6628f1b2…= (its own
=result= line from earlier). So the block's output *contains a UUID*.

=devops--log-async-result= (devops.el) logs the result after
=org-babel-insert-result= has replaced the placeholder with the output.
=devops-log--block-entry= then asks =devops-scripting--block-output= for
the block's =:id=, which calls =devops-scripting--block-run=
(devops-scripting.el:190). That function reads the ID like this:

: (string-match devops-scripting--uuid-regexp result)

The regexp is *unanchored*. It is meant to find the placeholder that
=#+RESULTS= holds while the run is going, but once the output is in
=#+RESULTS=, it finds the first UUID anywhere in it. That ID then matches
a run in the session, an old one, and the log line gets that run.

The same unanchored match is in =devops-scripting-block-output=
(devops-scripting.el:290), where it chooses between the pool's sessions.
So =devops-bb output FILE LINE= can answer with the wrong run too, for a
block whose output holds a UUID. Log, ID and session names are common
in devops output, so this is not rare.

The code already has the right test: =devops-scripting--placeholder-p=
(line 228) anchors the UUID with =\`...\'= after =string-trim=.

** Effect

- A consumer that pairs =execute= and =result= by ID, and reads output
  with =run-output ID= (devops.bb's =follow=, the dashboard and the
  planned =export=), gets the wrong run's output, silently.
- A =result= line can name a run that is not the one that finished, so
  the dashboard shows one run done and another never done.
- Only blocks whose output contains a UUID are hit, so a test with
  =echo hi= passes.

* Suggested fix

One helper in devops-scripting.el, used at both places:

#+begin_src emacs-lisp :eval no
(defun devops-scripting--placeholder-id (result)
  "Return the run ID RESULT is the placeholder for, else nil.
Only a RESULT that is nothing but the UUID counts: output that mentions
a UUID is output."
  (and (devops-scripting--placeholder-p result)
       (string-trim result)))
#+end_src

- =devops-scripting--block-run=: =id= becomes =(devops-scripting--placeholder-id result)=.
- =devops-scripting-block-output=: same for its =id=.

Then a finished block has no =id= from =#+RESULTS=, and
=devops-scripting--block-run= falls back to the latest run that sent the
block's body (its second branch). That is the existing rule for a
finished block; it was just never reached when the output held a UUID.

Better, and cheaper, for the log: the async filter *knows* the ID it is
delivering. Where a result is logged (=devops--log-async-result=), pass
that ID to =devops-log-block= and use it instead of looking the run up
again from the buffer. Then the =result= line cannot disagree with the
=execute= line, whatever the output says. The helper above stays, for
=devops-scripting-block-output=, which has no ID to start from.

Question: can =devops--during-async-filter= get the ID cheaply from
ob-comint's filter? If not, the helper alone is enough.
